## 1. Fix appliqué : 404 sur /checkout

**Problème** : le lien "Commander" des offres sur `/easyreadvoice` pointe vers `/checkout?plan=easyreadvoice-{plan.id}`, mais aucune page `app/checkout/page.tsx` n'existait (seuls `app/checkout/success` et `app/checkout/cancel` existaient) → 404.

**Corrigé** : création de `app/checkout/page.tsx` (calqué sur le style existant de `checkout/success` et `checkout/cancel` — Header/Footer, Suspense + useSearchParams, spinner Tailwind) :
- lit le paramètre `plan` dans l'URL,
- affiche un écran de redirection avec spinner ("Redirection vers la page de paiement sécurisée...")
- appelle `POST /api/stripe/create-checkout` avec `{ productId: plan }`
- redirige vers `data.url` (session Stripe) si succès
- en cas d'erreur (réseau, ou réponse sans `url`), affiche un écran d'erreur avec le message et un lien de retour vers `/easyreadvoice`
- `npx tsc --noEmit` : aucune erreur.

**⚠️ Le fix ne suffit pas à rendre l'achat fonctionnel** (voir finding #4 — Haute) : la page fonctionne correctement, mais l'API `create-checkout` répondra "Produit non trouvé" pour les 4 offres actuelles, car aucun `Product` en base ne correspond aux ids envoyés.

**Déploiement** : le code est en place sur DEV (`/root/newappai/app/checkout/page.tsx`) mais **pas encore déployé en production** (PJP sert le build standalone existant). Le déploiement (`scripts/deploy-easyreadvoice.sh`) rsync l'intégralité du code source vers PJP, rebuild et redémarre le serveur live (coupure de quelques secondes) — action non lancée volontairement, en attente de confirmation explicite car elle sort du périmètre strict "ne modifie rien d'autre" et il y a par ailleurs des modifications non liées déjà présentes sur DEV (`AGENTS.md`, `CLAUDE.md`, `PROJECT_CONTEXT.md`, `.codebase/project.json`) qui seraient embarquées dans le même déploiement.

## 2. Sécurité

### CRITIQUE — Clé Supabase `service_role` committée dans git
`.env.build` (suivi par git, non couvert par `.gitignore`) contient, malgré le commentaire "dummy/placeholder — never used in production" :
- `NEWAPPAI_SUPABASE_SERVICE_KEY` : un vrai JWT `service_role` (accès admin complet à la base, contourne toute RLS)
- `NEWAPPAI_SUPABASE_ANON_KEY` et `NEWAPPAI_SUPABASE_URL` réels
- `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY=pk_live_...` (clé live, normalement sans risque car publique par design, mais confirme que le fichier mélange dummy et réel)

Seules certaines valeurs du fichier sont réellement factices (`STRIPE_SECRET_KEY=sk_test_dummy_build_only`, `ADMIN_PASSWORD=placeholder_build`). Le `service_role` key, lui, a toutes les caractéristiques d'une vraie clé de production.
**Recommandation immédiate** : régénérer la clé `service_role` côté Supabase, retirer `.env.build` du suivi git (`git rm --cached .env.build` + ajout au `.gitignore`), et purger l'historique git si le dépôt est ou a été public.

### CRITIQUE — Token GitHub en clair dans la config git
`git remote -v` sur DEV expose un Personal Access Token GitHub (`ghp_...`) directement dans l'URL du remote `origin` (`.git/config`). Toute personne avec un accès en lecture au serveur ou à une sauvegarde du repo peut l'extraire et pousser/lire sur les dépôts associés.
**Recommandation** : révoquer ce token sur GitHub, en générer un nouveau, et utiliser une méthode d'auth qui ne stocke pas le secret en clair dans `.git/config` (SSH deploy key, ou credential helper).

### CRITIQUE — Fuite de données via API sans authentification
Plusieurs routes API n'ont **aucun contrôle d'accès** :
- `GET /api/easyreadvoice/books` — sans paramètre, retourne **tous** les livres de **tous** les utilisateurs (email, titre, chemin de fichier serveur `/root/easyreadvoice-audio/...`, statut). Confirmé exploitable en prod : `curl https://newappai.com/api/easyreadvoice/books` renvoie les données d'un vrai utilisateur.
- `PUT /api/easyreadvoice/books` — permet de modifier n'importe quel livre (statut, `audio_path`, chapitres) en connaissant juste son `id` — id récupérable via la fuite GET ci-dessus.
- `POST /api/easyreadvoice/books/[id]/generate` — déclenche le traitement de n'importe quel livre sans vérifier son propriétaire.
- `GET /api/orders` — même schéma (sans param = toutes les commandes, tous clients). Actuellement vide en prod (`[]`) mais le code est vulnérable dès qu'il y aura des commandes.

**Recommandation** : ajouter une vérification de session (email de l'utilisateur connecté = `user_email`/`customer_email` demandé) sur ces routes, comme c'est déjà fait sur `audio/[id]` (route de streaming, qui elle vérifie bien l'auth Supabase).

### HAUTE — Écriture non authentifiée sur les settings du site
`PUT /api/settings` n'a aucune authentification : n'importe qui peut réécrire la configuration globale du site (couleurs, header, footer...) → risque de défacement.
**Recommandation** : protéger par la même auth admin que le reste du back-office (`ADMIN_PASSWORD` / session admin).

### HAUTE — Checkout inopérant faute de correspondance Produit
`POST /api/stripe/create-checkout` fait `prisma.product.findUnique({ where: { id: productId } })`. Or les 4 offres EasyReadVoice envoient `productId = "easyreadvoice-decouverte" | "easyreadvoice-essentiel" | "easyreadvoice-standard" | "easyreadvoice-integral"`, alors qu'en base il n'existe qu'**un seul** `Product` EasyReadVoice, avec un id UUID auto-généré (`1020f90c-...`), non aligné avec ces slugs.
**Conséquence** : après déploiement du fix, cliquer sur "Commander" affichera l'écran d'erreur ("Produit non trouvé") pour les 4 offres — le funnel de paiement reste cassé en pratique.
**Recommandation** (hors périmètre de cette mission, à valider avec toi) : soit créer 4 lignes `Product` avec des ids stables correspondant aux slugs `easyreadvoice-*` et aux bons prix (1.99€/4.99€/9.99€/...), soit faire évoluer `/checkout` ou l'API pour mapper `plan` → `productId` réel.

### HAUTE — Dépendances avec vulnérabilités connues
`npm audit --production` : 4 vulnérabilités (3 hautes, 1 modérée) :
- **Next.js** : SSRF via upgrade WebSocket, cache poisoning des réponses React Server Components, bypass de middleware i18n (Pages Router) — fix nécessite `next@16.2.10` (breaking change)
- **nodemailer ≤9.0.0** (haute) : injection de commandes SMTP (plusieurs CVE : CRLF injection, bypass `disableFileAccess`/`disableUrlAccess`) — fix disponible sans breaking change (`npm audit fix`)
- **ws 8.0.0–8.20.1** (haute) : divulgation mémoire non initialisée, DoS par fragments — fix disponible sans breaking change
- **postcss** (modérée) : XSS via sortie CSS non échappée — fix nécessite la mise à jour Next.js ci-dessus

**Recommandation** : lancer `npm audit fix` (sans `--force`) pour nodemailer/ws sans risque de breaking change ; planifier la montée de version Next.js séparément (impact plus large à tester).

### MOYENNE — Headers de sécurité HTTP absents
Aucun header de sécurité sur les réponses (`/` et les routes API) : pas de `Content-Security-Policy`, `X-Frame-Options`, `Strict-Transport-Security` (HSTS), `X-Content-Type-Options`. Le site est donc plus exposé au clickjacking, MIME-sniffing, et il n'y a pas de politique CSP pour limiter l'impact d'un XSS.
**Recommandation** : ajouter un `headers()` dans `next.config` (actuellement absent) pour définir ces headers globalement.

### BASSE — `x-powered-by: Next.js` exposé
Header par défaut de Next.js, révèle la stack technique. Désactivable via `poweredByHeader: false` dans `next.config`.

### BASSE — Fichier `.bak` dans le code des routes API
`app/api/easyreadvoice/books/route.ts.bak` traîne dans le repo (ancienne version avec un bug de syntaxe visible — template string cassé). Sans impact fonctionnel (Next.js n'expose que `route.ts`), mais pollue le repo et pourrait semer la confusion.
**Recommandation** : supprimer ce fichier (non fait ici, hors périmètre "ne rien modifier d'autre").

### Vérifications positives
- `.env` (le vrai fichier avec les secrets d'exécution) est bien listé dans `.gitignore` et **non tracké** par git — confirmé (`git ls-files` ne le liste pas).
- `GET /api/easyreadvoice/audio/[id]` (streaming des MP3) vérifie bien l'authentification Supabase et le propriétaire du livre — contrairement aux routes `books` listées plus haut.
- `/admin` redirige correctement (307) vers `/admin/login` pour un visiteur non authentifié.
- `app/api/uploads/[...slug]/route.ts` bloque correctement les tentatives de path traversal (`..`).

Impact modéré, à corriger progressivement.
